# Tuneable-Consistency

A Raft key-value store and a patched mongod whose server picks each request's consistency level from the client's SLA and a shadow price (Chameleon), with a workload driver, the fixed-level and Pileus baselines, and the scripts that run the experiments on CloudLab. This file covers building and running. The design is in DESIGN.md, the experiment plan and workloads in EXPERIMENT.md, the calibrated values in CALIBRATION.md, and the MongoDB port in MONGODB_PORT.md.

## Requirements

- Java 17 or newer and Maven, for the Java store and the driver.
- tmux, for local runs (`run_all.sh` runs the processes inside a detached session).
- Python 3 with pandas and numpy, for the config generators and the analysis scripts, and matplotlib for the figures of `analyze_run.py`.
- For CloudLab runs: an allocation of Ubuntu 22.04 or 24.04 machines reachable by ssh key. `setup_cloudlab.sh` installs everything the machines need, including the MongoDB build environment when asked.

Build the Java store and the driver from the repository root:

```bash
mvn clean install
```

## Configs

Every run takes one YAML config, which fixes the store (`transport: raft` or `mongodb`), the cluster, the geo topology, the SLAs, the workload phases and the calibrated server values (sMax, the hard cap, the replication budget). The arm is not in the config; it is chosen at launch (below).

| config | what it is |
|---|---|
| `config_local.yaml`, `config_regional.yaml`, `config_global.yaml` | the day sequence on the Java store, three geo topologies |
| `config_local_mongodb.yaml`, `config_regional_mongodb.yaml`, `config_global_mongodb.yaml` | the same on the patched mongod |
| `config_scale_<N>.yaml`, `config_scale_mongodb_<N>.yaml`, N in 3, 9, 15, 21, 27 | the server-count scaling configs, generated by `make_scale_configs.py` |
| `config_failure_leader_global.yaml`, `config_failure_follower_global.yaml` | the failure experiment (Java store only), generated by `make_failure_configs.py` |
| `config_random_<n>.yaml` | a random-SLA config, generated by `make_random_config.py --seed <n> --write-rate "5;20;50;80" --duration 120`; the config's own seed is n |

The generators derive their output from the base configs, so after a change to a base config, rerun the generator rather than editing the derived file.

## Running locally

```bash
./run_all.sh [label] [config.yaml]       # default config: config_local.yaml
```

The script checks for Java 17+, Maven and tmux, builds the project, writes the runtime classpath to `target-script/classpath.txt`, and runs one `ServerNode` JVM per Raft node plus the `WorkloadDriver` JVM in a detached tmux session named `tuneable`. Everything runs with `runs/<label>_<timestamp>/` as its working directory, so run.log, the client ledger, the occupancy streams and the server logs land there. The terminal blocks until the run completes; on failure the tmux session is kept for inspection. `run_all.sh` starts the Java store only; a mongod config runs through the CloudLab scripts below, which start the patched binary.

To start the processes by hand instead, run each node with `java -cp <classpath> org.example.Server.ServerNode <config.yaml> <serverId>` and then the driver with `java -cp <classpath> org.example.Client.WorkloadDriver <config.yaml>`.

## Running on CloudLab

Every CloudLab script takes either a single machine (`<user@host> <ssh-key>`), where the servers and the driver share it and the geo topology is emulated on loopback, or `--hosts <file> --key <ssh-key>`, one machine per server plus one for the driver. The experiments in EXPERIMENT.md use the second layout.

The hosts file has one line per machine: the role, the ssh target this laptop uses, and the machine's address on the experiment network. Exactly one `client` line and one `server` line per Raft node, in node order; the first server is node 0, the preferred leader. See `hosts.example.txt`:

```text
# role    ssh target                lan ip
client    user@host1.cloudlab.us    10.10.1.1
server    user@host2.cloudlab.us    10.10.1.2
server    user@host3.cloudlab.us    10.10.1.3
```

The workflow, with `hosts.txt` standing for your hosts file:

```bash
# once per allocation, and again after a reboot or reimage: installs the dependencies and
# sets the experiment interface to MTU 9000, which the run script checks; --mongodb also
# provisions the MongoDB build environment (about 60 GB and an hour) on the first server
./setup_cloudlab.sh --hosts hosts.txt --key ~/.ssh/cloudlab [--mongodb]

# once per change to the mongod patch: builds the patched mongod on the first server and
# copies the binary to the other servers; needed before any mongodb config runs
./build_cloudlab.sh --hosts hosts.txt --key ~/.ssh/cloudlab

# one run: builds the jar locally, ships it with the config, applies the delay rules, runs
# the servers and the driver in remote tmux sessions, and fetches the artifacts into
# runs/<label>_<timestamp>/
./run_all_cloudlab.sh --hosts hosts.txt --key ~/.ssh/cloudlab [--seed <n>] <label> <config.yaml>

# a sweep over arms, seeds and configs (and optionally --smax values), one run after another
./run_all_cloudlab_sweep.sh --hosts hosts.txt --key ~/.ssh/cloudlab \
    --modes "chameleon;chameleonPileus;pileus;strongest;weakest" --seeds "7;42;100" \
    "config_local.yaml;config_regional.yaml;config_global.yaml"

# after an interrupted run (Ctrl-C, a dropped ssh, a hung driver): removes the remote tmux
# session, the processes, the delay rules and the per-site aliases, keeps finished runs
./clean_cloudlab.sh --hosts hosts.txt --key ~/.ssh/cloudlab
```

The arms (`--modes`) are `chameleon` (the server decides, nearest-node routing), `chameleonPileus` (the server decides, Pileus routing), `pileus`, `strongest` and `weakest`. A sweep takes at least one of `--modes`, `--smax` and `--seeds`, and names each run `runs/<config>_<mode>_<sMax>_<seed>/`; it refuses to start a run whose folder already exists, so move or delete the old folder first. Without `--smax` the config's calibrated sMax is used. A single run can override the config's seed with `--seed`.

Notes for distributed runs:

- The runner rewrites `cluster.serverHosts` to the machines' experiment-network addresses and gives the client machine one alias per client site from `--site-subnet` (default `10.99.0.0/24`), so two sweeps running at the same time on different machines must use different subnets.
- Before starting, the runner compares every machine's clock with NTP and refuses to run if one is more than 2 ms off; the error names the machine and the `chronyc makestep` that fixes it.
- Delays are applied on each machine's experiment interface only, so ssh on the control interface is unaffected.
- On Ctrl-C the experiment keeps running remotely and the script prints how to attach, clean up and fetch by hand.

## Run output

Each run folder holds the driver's `run.log` (one progress line every 5 s with the phase, served, rejected and realized profit), the client ledger `client_metrics_global.csv.gz` (one row per node, site and level per second with counts, latency percentiles and a latency histogram), one `occupancy_<i>.csv.gz` per server (utilization, in-flight and the price per 100 ms), and for the Java store one `server_drain_<i>.csv.gz` per server (admissions and refusals by cause) and the server logs. `config.yaml`, `hosts.txt` and `run_info.txt` record what ran where.

`analyze_run.py <run folder>` prints the per-phase and per-level report of one run; `--save` writes its figures as PNGs to `<run folder>/graphs` (or `--out <dir>`) and `--plot` opens them. `analyze_runs.py <config> --modes "..." --smax "..." --seeds "..."` compares the runs of one config across arms, sMax values and seeds, with the seed average beside the per-seed rows; it reads `runs/` unless given `--runs-dir`. Finished runs are kept under `results/<family>/`, one subfolder per experiment family.
