# Porting Chameleon to MongoDB

Implementation plan for running every arm (strongest, weakest, pileus, chameleon, plus MongoDB's native overload control) on a patched mongod, with the Java WorkloadDriver as the client. Decisions taken: all five arms in MongoDB; execution cost estimated per query shape at admission; the Java driver reused with a new transport; MongoDB pinned at commit 6d990ba (master, Sep 10 2026). Paths under `mongo/` are relative to `mongo/src/mongo/`.

## What changes and what does not

The decision algorithm, the SLA format, the price controller, the histograms, the occupancy meter, the client routing rules, the grading rules and the phase schedule are unchanged. Three premises of DESIGN.md do not hold in MongoDB and are stated here once so no later section has to re-argue them.

- Linearizable reads are primary-only and are confirmed by appending a noop oplog entry after the read and waiting for w:majority on it (`db/read_concern_mongod.cpp:577-588`). There is no ReadIndex and no follower-served linearizable read. The replication bucket charges one entry per linearizable read.
- A write command produces one oplog entry per modified document (`db/update/update_util.cpp:497`, `db/op_observer/op_observer_impl.cpp:760-886`), so the replication charge is nModified, unknown until the predicate has run. The bucket charges an estimate at admission and trues up at completion.
- Service time is not a function of level alone. Latency under level c is exec(shape) + wait(c, gap), with exec independent of the level and the waits single, per-command and independent of the query (`db/service_entry_point_shard_role.cpp:2004`, `:1468`, `:1265`). The histogram is factored accordingly: one exec histogram per shape, one wait histogram per (level, gap bucket), combined per request.

Two further differences are behavioral, not structural, and are reported as such: the session frontier is the serving node's lastApplied rather than the read value's own position, so causal gaps are larger than in the Java store; and lastApplied on a secondary advances at oplog batch boundaries, so the causal wait histogram has a floor.

## Level mapping

| DESIGN.md level | MongoDB request | Wait | Where enforced |
|---|---|---|---|
| eventual-local | readConcern local, no afterClusterTime | none | read source lastApplied on a secondary, untimestamped on the primary (`db/shard_role/shard_catalog/snapshot_helper.cpp:64-119`) |
| eventual-majority | readConcern majority, no afterClusterTime | until a majority snapshot exists (usually none) | `db/read_concern_mongod.cpp:417-482` |
| causal-local | readConcern local + afterClusterTime T | lastApplied >= T | `db/repl/replication_coordinator_impl.cpp:2001-2010` |
| causal-majority | readConcern majority + afterClusterTime T | commit point >= T | same |
| linearizable | readConcern linearizable, primary only | noop write + majority ack after the read | `db/read_concern_mongod.cpp:540-594` |
| wc:k | writeConcern w:k | k nodes at lastApplied >= opTime, once per command | `db/repl/topology_coordinator.cpp:1342-1385` |
| wc:majority | writeConcern w:majority | committed snapshot >= opTime | `db/repl/replication_coordinator_impl.cpp:2212-2251` |

The session frontier is the hybrid logical timestamp the driver returns as operationTime on every reply and sends back as afterClusterTime. The gap is that timestamp minus the node's lastApplied (causal-local) or minus the commit point (causal-majority), converted to milliseconds of lag using the wall time stored beside each optime, and bucketed with the existing gap edges rescaled to time.

## Milestone 0: environment

1. Build step, separate from the run step, on the same CloudLab host that runs the cluster (the whole replica set is five processes on one host with loopback addresses, as today). The bazel build fetches MongoDB's own hermetic compiler toolchain, and Ubuntu 24.04 x86-64 is a supported platform (`mongo/bazel/toolchains/cc/mongo_linux/mongo_toolchain_version_v5.bzl:150`), so no compiler is installed on the host; the host needs Python 3, libcurl and liblzma headers, and about 13 GB free. Install bazel with `python buildscripts/install_bazel.py`, build with `bazel build install-mongod --disable_warnings_as_errors=True`. A `build_mongod.sh` script is idempotent: it computes a build id from the pinned commit plus a hash of the patch, skips the build when a `mongod` with that id is already present, and otherwise builds and stamps the binary with the id. Because a CloudLab instance is usually but not always reused, the finished binary and its id are also copied to the project's persistent storage, and the script checks there before building, so a fresh instance costs a copy rather than a rebuild. Expect well under an hour for the first build on a many-core host and minutes for incremental ones after a patch change.
2. Cluster launch: a MongoDB variant of `run_all_cloudlab.sh`. Same five loopback addresses 127.0.1.1 to 127.0.1.5 and the same tc/netem rules. Each mongod starts with `--replSet rs0 --bind_ip 127.0.1.k --port 27017`. `rs.initiate` with node 0 at priority 10 and the others at 1 so the leader is at region A as in EXPERIMENT.md, and each member tagged `{node: "k"}` so the client can address it by tag. `writeConcernMajorityJournalDefault` left at its default; `enableMajorityReadConcern` is always on in this tree.
3. Client sites: the MongoDB Java driver has no public option to bind a source address, and the netem rules key on it. The transport binds it one level down instead: each site gets its own MongoClient whose Netty socket channel class connects from that site's 127.0.2.x address (MongoTransport.SiteBoundChannel), so the WorkloadDriver stays one process with one ledger and the existing delay rules apply unchanged. This replaces the network-namespace-per-site approach considered earlier; it needs no root and no per-site processes. The servers need the same treatment: mongod never binds its outgoing sockets, so its replication and heartbeat connections leave from 127.0.0.1 and match no delay rule, and in the first geo smoke a w:3 write from the Virginia site acknowledged in 4.7 ms with secondaries configured 30 to 160 ms away. `bindsrc.c`, a 60-line `LD_PRELOAD` shim compiled by `build_mongod.sh` into `libbindsrc.so` beside the binary, binds every outgoing IPv4 TCP connection of the process to `BINDSRC_ADDR`; the runner loads it into each mongod with the node's own address, which gives inter-server traffic the same (source, destination) pairs the Java servers produce. It works unchanged for the control and stock binaries, which also link glibc dynamically.
4. Data load: one collection, `_id` keys "user0" to "user<keySpace-1>", a second indexed field for the range-scan shape (Milestone 5), loaded before the run with w:majority so the followers start caught up.

Deliverable: five patched or stock mongods in a replica set with the geo delays applied, a shell smoke test showing a causal read waiting on a lagging secondary.

## Milestone 1: mongod measurement plane (mode-independent)

A new module `db/chameleon/` compiled into mongod. Everything here runs in every arm so that the arms differ only in who decides.

1. Server parameters (`db/chameleon/chameleon.idl`, pattern in `db/admission/ingress_admission_control.idl`): `chameleonMode` (off | server), `chameleonSMax`, `chameleonReplicationBudgetPerSecond`, `chameleonMaxWaitMs`, `chameleonControlIntervalMs`, `chameleonUTarget`, `chameleonEta`, `chameleonLambdaMin`, `chameleonHistogramDecay`, and `chameleonSlaTable`, a JSON string holding the read and write SLA tables from config_global.yaml, parsed into a port of SlaRegistry. All settable at runtime so the driver configures the cluster the way AdminService does today.
2. Request envelope: the SLA identity, the RTT estimate and the client-decided target ride in the generic `comment` argument as a BSON document `{app, sla, rtt, wantLinearizable, requestedWriteConcern, waitBound}`. This needs no IDL change and the driver's runCommand passes it through. A dedicated generic argument in `idl/generic_argument.idl` is a later cleanup, not a requirement.
3. Reply envelope: appended next to operationTime in the reply metadata path (`db/service_entry_point_shard_role.cpp:378-396`) as `$chameleon: {level, wc, lastApplied, commit, readTs, serviceMs, predicted, waited, fellBack, rejected, entryTs}`. `readTs` is the snapshot timestamp the read used; `entryTs` is the last opTime the write produced. The client grades from these exactly as it grades from the KV reply today.
4. Timers: `t_recv` is the CurOp start already taken at message receipt. Add `readConcernWaitMicros` and `linearizableWaitMicros` to OpDebug, timed around the two wait calls; `waitForWriteConcernDurationMillis` already exists. Exec time is total elapsed minus the three waits.
5. Histograms: a port of ServiceTimeHistograms as a ServiceContext decoration, with the wait cells keyed by (level, gap bucket) and the exec cells keyed by shape (Milestone 5; until then a single exec cell). Samples are filed from `CurOp::completeAndLogOperation` beside the existing `finalizeOperationStats` call (`db/curop.cpp:907-910`). Counters are per-thread partitioned and folded on the refresh tick, replacing the DoubleAdder.
6. Occupancy meter: `on_event(+1)` in `_initiateCommand` for every operation subject to ingress admission control, `on_event(-1)` at completion. The price controller is a PeriodicRunner job on `chameleonControlIntervalMs`, modeled on `FlowControlRefresher` (`db/admission/flow_control.cpp:221-233`). It publishes u, lambda, in-flight and role through a `chameleon` serverStatus section; the driver polls it every interval and writes `occupancy_<n>.csv` in the existing schema.
7. Replication bucket: a port of ReplicationRateBucket on the primary. Charged at admission with 1 for a single-document write or a linearizable read, and with the shape's decayed mean nModified for a multi-document write; trued up at completion from OpDebug's nModified, ninserted and ndeleted. An empty bucket is the hard backstop for writes.

Deliverable: stock arms run unchanged through the patched server; slow-query logs show the new timers; the serverStatus section reports u and lambda; a unit test in `db/chameleon/` reproduces the worked example in DESIGN.md step 4.

## Milestone 2: the decision path (chameleonMode = server)

Hooked into `ExecCommandDatabase::_initiateCommand` after read and write concern extraction and after ingress admission (`db/service_entry_point_shard_role.cpp:1488`, `:1874-1884`), only for commands carrying the envelope.

1. Legal levels: a secondary excludes linearizable; writes on a secondary already fail with NotWritablePrimary, which the client treats as the redirect. Look up the SLA by (app, sla) and the command's read/write type.
2. Gaps: afterClusterTime from the read concern args against `getMyLastAppliedOpTime()` and `getLastCommittedOpTime()`.
3. Score: a C++ port of RungScorer using the combined CDF (exec cell shifted or convolved with the wait cell) and omega as the sum of the two means. Uncalibrated cells are free and certain with the rider cap, as today.
4. Admit or reject: reject when max V_c <= 0, when the occupancy hard cap is hit, or when a write finds the bucket empty. Rejection is a uassert with a new error code carrying the SystemOverloadedError label, the same label the ingress rate limiter uses, so the driver's retry logic treats it as terminal.
5. Apply the choice: overwrite the operation's ReadConcernArgs with the chosen level, keeping afterClusterTime for the causal levels and dropping it for the eventual ones, and overwrite the write concern with w:k and wtimeout equal to the wait bound. Set the wait bound as an artificial deadline around `waitForReadConcern` only (`OperationContext::pushArtificialDeadline`).
6. Fallback on expiry: a read concern wait that times out is caught, the read concern is downgraded to local without afterClusterTime, and the command proceeds; the reply is graded at what it delivered. A linearizable confirmation that times out returns the already-read result marked as local (`waitForLinearizableReadConcern` takes the bound instead of the current zero at `:1265`). A write concern that times out replies with the number of nodes that had reached the opTime, computed with the topology coordinator's reached-opTime helpers, as the delivered concern.
7. Sample filing follows DESIGN.md step 8: the sample goes to the chosen level's cell, at the bound on expiry, nothing under the fallback level.

Deliverable: the chameleon arm runs end to end on a local no-delay cluster; predicted versus realized profit is within the same error band as the Java system on the same phase schedule scaled to C.

## Milestone 3: the Java harness

1. Transport: a `MongoTransport` implementing the interface KvFramedTransport exposes to KvSessionClient (RequestHandle, RpcFailure), so the session client, grader, Pileus selector, RTT estimator and ledger are untouched. It translates a KvRequest into a raw find or update command document with readConcern, writeConcern and the comment envelope, issues it with `runCommand(doc, readPreference)`, and translates the reply plus `$chameleon` into a KvResponse. runCommand is required because the fluent API discards unknown reply fields. The only new dependency is `org.mongodb:mongodb-driver-sync` from Maven Central; the stock library is a courier for BSON documents and needs no modification, since the envelope travels in the standard `comment` argument and the reply is returned whole.
2. Clients and routing: one MongoClient per site process, shared cluster clock. Reads target a node with read preference `secondary` or `primary` plus the tag set `{node: k}`, so the driver's own selection collapses to the node the harness chose. Writes target `primary`. A NotWritablePrimary error is the redirect; the leader hint is refreshed from the topology the driver already monitors. serverSelectionTimeoutMS is set low (200 ms) so an unreachable target surfaces as a transport failure, not a 30 s stall.
3. Frontier: the harness carries it, not the driver. KvSessionClient already tracks a session index; the transport writes it into `readConcern.afterClusterTime` for the causal levels and advances it from the reply's readTs or entryTs, exactly as the KV protocol does today. No ClientSession or causal-session feature is used. The driver still gossips `$clusterTime` on every command from its per-client cluster clock, which is what lets a lagging secondary accept an afterClusterTime ahead of its own lastApplied; one MongoClient per site keeps that clock fresh because every site sees replies from the primary.
4. Index width: Raft indices are int32 in the proto and the Java code; MongoDB timestamps are 64-bit. Change sessionIndex, valueIndex, logIndex, commitIndex, localValueIndex and committedValueIndex to int64 and the Java fields to long. This is mechanical but touches the client, the grader, the ledger and the tests.
5. Connection pools: each in-flight operation holds one connection and one server thread. Set maxPoolSize per site well above the expected in-flight count at the target rate, and count pool wait inside end-to-end latency. Verify with the occupancy meter that the server, not the pool, is the saturating resource before calibrating S_max.
6. Arms: strongest and weakest send the rung's level and concern explicitly; pileus sends the selector's choice; chameleon sends only the envelope; the native overload arm is strongest with `ingressRequestAdmissionRatePerSec` and `ingressAdmissionControllerTicketPoolSize` set to calibrated values on every node.
7. Hooks off (`mongodb.serverHooks: false`, weakest and strongest only): the driver pushes no parameters, so `chameleonEnabled` stays at its server default of false and the hooks return at their first check; the client still puts the level and concern on the wire itself, so the requests execute exactly as in the hooks-on arm and still carry the comment envelope (same bytes on the wire). Grading substitutes stock reply metadata for the envelope: `operationTime` for the read timestamp and the write's opTime, the requested level and concern as delivered, commit point and server-side service time explicitly unknown (no free-upgrade credit; the RTT estimator sees service time). Occupancy rows come from `globalLock.activeClients.total` and the `repl` flags of `serverStatus`. Two uses: the hooks' cost is the difference between the fine capacity probe with and without the switch on the same binary (throughput, latency, CPU, not profit), and the same switch lets the harness run against an unpatched or stock mongod as a MongoDB-as-shipped baseline.
8. Write deadlines and the driver: a `writeConcernError` whose code is in the execution-timeout category (a `maxTimeMS` expiry during the replication wait, code 50) makes the Java driver mark the server UNKNOWN and stall every request bound for it until the next heartbeat completes (`DefaultSdamServerDescriptionManager`, driver 5.11.1). The acknowledgment wait must therefore end through `wtimeout` (code 64, an ordinary write-concern error graded as a fall-back, the Java store's bounded wait) and never through `maxTimeMS`. First attempt: with the hooks on, `applyWriteConcern` clamps the wait to the smaller of the wait bound and the operation's remaining deadline minus 10 ms and the command kept `maxTimeMS`. Not enough: in the overload diagnostic (`runs/stormgeo2_20260916_230741`, 120,000 requests/s under geo, the transport's new driver-event listeners) every site marked the primary UNKNOWN one to five times in 70 s, each time with that exception, and the episodes produced 760,000 failed server-selection attempts (writes and their retries), the dominant failure above the knee; under a 60,000-thread box a 10 ms margin does not order two timers. So a write now carries no `maxTimeMS` in either mode: with the hooks on the wait is bounded by the envelope's waitBound and the server's maxWaitMs, without them by `wtimeout` set to the remaining deadline. A write late in execution is graded late by the client, which is how the Java store treats its writes too (it never cancels a write at the deadline). The server-side clamp stays in `applyWriteConcern` as a guard should a deadline ever be set. Reads keep `maxTimeMS`; its expiry there is a plain `MongoExecutionTimeoutException`, which the transport now grades as deadline exceeded (it is not a `MongoCommandException`, so the previous code-50 mapping never fired for it).
9. Driver logging: `src/main/resources/simplelogger.properties` sets the MongoDB driver's loggers to WARN for every main in the jar. The INFO line the driver prints when a request waits for server selection produced a 2.9 GB run.log under overload.
10. The per-shape execution histogram is consumed only by the exec estimator (`chameleonExecEstimatorMode` 1 or 2, default 0). The shape key and the exec sample are now computed only when the estimator is on, in every arm; with it off the measurement plane is the envelope parse, occupancy, wait cell, backstops, bounds, and reply envelope. Verified on build `6d990baca59c-21cdf984cb77ebbf-opt` with the strongest arm at a flat 230,000 offered for 100 s, hooks on and off (`runs/verify-hooks_20260916_202001`, `runs/verify-nohooks_20260916_202321`): run.log 5 KB in both, zero driver waiting lines, the primary never marked UNKNOWN, no `writeConcernError` code 50 anywhere; the hooks-off run shows 983 code-64 `wtimeout` expiries, the intended path. The unit test passes. Observed in passing and left for the strongest arm's calibration: at 230,000 offered every write and linearizable read targets the primary, whose per-site pools (2000) fill; pool checkout timeouts surface as transport failures (3.8 M with hooks on, 2.2 M off), the session client retries a failed request round-robin as in the Java store, and the retried writes come back as redirects (7.0 M and 4.3 M). Served at saturation was 135,000 with hooks on against 152,000 off, a larger gap than weakest's 4 to 5%, with 242,000 bounded linearizable fall-backs against 2,000; the primary logged no slow operations with hooks on and 21,000 without, so the bounded waits shift where the overload lands. Strongest's own capacity is the primary's and is well below 170,000; its C and pool size need their own probe. The run script no longer passes `--setParameter chameleonEnabled=false`, which is the default and which a stock binary would reject, and `mongodb.binaryPath` (requires the hooks off) points a run at another binary on the node: `config_mongodb_capacity_probe_fine_control.yaml` runs the unpatched pinned commit and `_stock.yaml` the 8.2.12 release, both at `~/tuneable/<control|stock>/mongod`. First measurement (one matched pair of fine probes, opt binary, weakest, geo off): below the knee both serve the offered rate in full (147,000 and 169,500 requests/s served against 148,000 and 169,700 offered, with and without hooks); at saturation the plateau is 175,000 to 177,000 served with the hooks against 183,000 to 184,000 without, so the hooks cost about 4 to 5% of capacity, with both configurations at the same total CPU (the box saturated, about 42 threads of mongod and 17 of client). Violation and deadline counts are not comparable across the pair because the hooks-off grading lacks the commit point. A four-way run of the same fine probe under the harness, weakest, geo off, back to back on the same node (`runs/fourway-*`): stock 8.2.12 serves the offered rate in full through 210,000 requests/s and plateaus at 209,000; the unpatched control (master 6d990ba, opt) serves in full through 190,000 and plateaus at 186,000 to 187,000; ours with the hooks off plateaus at 181,000 to 182,000; ours with the hooks on serves 185,000 of 190,000 and plateaus at 173,000 to 174,000. All four saturate the box at the same CPU (about 40 to 44 hardware threads of mongod, 17 to 20 of client), so the ladder is throughput per unit of machine: stock to control about 12% (release branch plus profile-guided optimization), control to hooks-off about 3% on that single pair; an interleaved harness A/B of three rounds each (`runs/ab*-control`, `runs/ab*-oursoff`) pins it at 1.7% of saturated throughput (plateau 185,800 [183,300 to 187,400] against 182,500 [180,900 to 184,200]), zero below the knee (188,800 against 188,400 at 190,000 offered), consistent in direction in five of six comparisons; the standalone A/B saw no CPU-per-operation difference at the 0.1% level, so the residual is a saturation-only effect, most plausibly code layout, and is below anything the arm comparison can see since every arm runs the same binary, hooks-off to hooks-on about 4 to 5% (the measurement plane). The stock and control runs also confirm that the harness runs unmodified against an unpatched or stock mongod with `serverHooks: false` and `binaryPath`; a poller bug found by the control run (activeClients.total is int64 on master, int32 in 8.x) is fixed and covered by a unit test.

Deliverable: all five arms run against the patched cluster from the existing config files, with a `transport: mongodb` key selecting the transport and the ledgers in the existing CSV schema.

## Milestone 4: calibration, scripts, analysis

1. Capacity C: the existing sweep against mongod. Expect several times lower than the Java store. Scale the phase rates by C as EXPERIMENT.md prescribes. Done: C = 100,000, the knee on the global topology (MONGODB_BASELINES.md 3f); the day sequence and the new static load sweep (`config_mongodb_loadsweep.yaml`) are expressed against it.
2. S_max: the existing `sweep_smax.sh` logic against the serverStatus occupancy reading, at the latency knee. Done: 450, the primary's mean in-flight at the knee, confirmed with the chameleon arm regulating to the 0.85 target at 0.8C (MONGODB_BASELINES.md 3i).
3. Replication budget: measured maximum oplog rate on the primary with w:1 point updates, times 0.8. Done: 85,000 from a 105,800 writes/s ceiling on the isolation topology (MONGODB_BASELINES.md 3i).
3a. Pool cap: `maxPoolSize` 1,000 per site and node, from a three-point probe at 120,000 under geo (MONGODB_BASELINES.md 3i); the runner's fd limit is 262,144 so the client never runs out of descriptors. Open question found in the S_max run: at 1.8C every pool fills, requests that die in the client pools never reach the occupancy meter, the inflated client RTT estimate makes the scorer refuse, and admission-aware routing then sends traffic to farther nodes whose pools fill in turn. The Java store's multiplexed transport has no such cap. Options are to accept it as a property of the system under test and describe it, to grade a pool checkout timeout as a client-side rejection (the analogue of the Java ingress cap, which also refuses before the request costs anything), or to exclude pool wait from the RTT estimate the client sends; decision pending.
3b. Geo smoke on the final configs (`runs/geosmoke3-*_2026091[67]_*`, 40 s at up to 2,000 requests/s, all four arms, sMax 450, budget 85,000, cap 1,000, writes without maxTimeMS): weakest 64,269 of 64,300 responses, strongest 64,240, pileus 64,282, chameleon 62,241 with 2,017 rejected (the scorer's far-site refusals, 1,981 in the previous smoke) and 591 violations against 751; zero lost in every arm, no node marked UNKNOWN, no pool cleared, and the only transport errors are 31 to 63 server-selection timeouts per run in the first second while far sites discover the cluster. Chameleon's realized profit per 5 s window is unchanged from the previous smoke (82,866 against 83,034).
4. Native overload arm: rate limiter set to C, ticket pool set to S_max, so it sheds at the same capacity as chameleon but in arrival order.
5. Analysis: `analyze_run.py` unchanged except for merging per-site ledgers.
6. Overhead: `db/service_entry_point_shard_role_bm.cpp` before and after the patch, reported as microseconds per command.

## Milestone 5: shape-keyed execution cost

1. Admission-time shape key: the real query shape hash is computed inside the command, after admission. Compute a lightweight key in `_initiateCommand` from the raw command: command name, collection, sorted top-level predicate field names, operator set, presence of sort and limit, and the multi flag. Record the real queryShapeHash at completion and assert offline that the lightweight key never merges two real shapes.
2. Exec histogram per key with the same decay and eviction of cold keys; the wait histogram is unchanged. Combination by shifting the wait CDF by the exec mean, with convolution as a switch for the ablation.
3. Workload: add one range-scan shape on the indexed field under an existing read SLA, with a cardinality drawn from a wide distribution, so the exec term varies within the shape.
4. Ablation: `chameleonExecEstimator` = none | shape | shape-convolved, reported as prediction error and realized profit.

Deliverable: the estimator ablation table for the global topology.

Deferred to future work (decided 2026-09-16): a range-read shape in the main workload was considered for realism and rejected for now, because the arm comparison needs point operations only (exec constant, estimator off, arms differ only in the decision) and a range shape would change C, add an SLA with scan-scale thresholds, force the estimator on in the chameleon arm, and raise the per-document versus absolute rung question. If revisited: 5 to 10% of reads under a new SLA per application, cardinality log-uniform over 1 to 1000 documents with a limit, absolute rungs sized so the largest scans sit near the top threshold, estimator mode 1 by default in chameleon, and the point-only configs kept as the cross-system comparison since the Java store has no sorted index.

## Order and effort

Milestones 0, 1 and 3 are independent of each other after the envelope format is fixed, and can proceed in parallel. Milestone 2 depends on 1; Milestone 4 on 2 and 3; Milestone 5 on 4. Rough sizes for someone who knows both codebases: Milestone 0 a few days dominated by the first build; Milestone 1 about a week; Milestone 2 about a week; Milestone 3 about a week including the int64 change; Milestone 4 a few days plus machine time; Milestone 5 about a week. The build and test loop on mongod is the main schedule risk, so keep the patch confined to `db/chameleon/` plus small hooks in the entry point, curop and read_concern_mongod so that incremental builds stay short.

## Decisions recorded

1. Client sites keep their per-site source addresses for the netem rules, but through the transport rather than through network namespaces: the MongoDB transport binds each site's address inside its Netty socket channel (Milestone 0, item 3), so the WorkloadDriver remains one process. Namespaces were the earlier choice and are no longer needed.
2. Indices change from int32 to int64 in the proto and the Java code on the main branch, since the experiments have not been rerun since the last changes and a MongoDB-only branch would fork shared code.
3. The build is a separate step from the run, on the same CloudLab host, with an idempotent build script that skips the build when a binary with the current build id exists locally or in persistent storage (Milestone 0, item 1). The build always passes `--config=opt`. MongoDB's default bazel profile, `fastbuild`, is an unoptimized debug build (opt off, dbg on, debug assertions compiled in, a 1.6 GB binary), and the first smoke and probe runs were unknowingly made with it: measured standalone on CloudLab it spent about 0.65 ms of CPU per point read and peaked near 58,000 point reads per second on 64 threads, roughly ten times slower than a release mongod. The bazel profile is part of the build id so a cached debug binary is never reused, and every capacity number comes from the opt binary.
4. Implementation is under way (status below); nothing is committed.

Wire formats fixed by this implementation:

- Request envelope in `comment`: `{app, sla, rtt, read, frontier?, target?, wantLin, wc, waitBound}`; the frontier is a BSON timestamp, the target a ReadLevel ordinal.
- Reply envelope `$chameleon`: `{level, wc, lastApplied, commit, readTs | entryTs, serviceMs, predicted, waited, fellBack, rejected, epochMs}`; the client derives `logIndex`, `commitIndex`, `valueIndex`, `localValueIndex` and `committedValueIndex` from these (a read at or below the commit point is majority-committed state).
- Sample filing: the wait cell (level, gap bucket) receives the request's wait component, read concern plus linearizable plus write concern waits, at the bound when the wait was abandoned; the shape cell receives total service time minus waits. Latency under a level is scored as exec + wait, by shift or convolution per `chameleonExecEstimatorMode`.

CloudLab procedure, one script per cadence, all driven from the local machine:

1. Once per machine: `./setup_cloudlab.sh <user@host> <key> --mongodb`. Installs the build dependencies, fetches the single pinned commit of mongodb/mongo into `~/mongo` on the host, and installs bazel. Idempotent; re-run after a reimage.
2. Once per change to the patch: `./build_cloudlab.sh <user@host> <key>`. Exports the patch from the local `mongo/` clone, resets the host's checkout to a clean tree, applies the bundle, and runs `build_mongod.sh` inside a remote tmux session with the `opt` profile, leaving `~/tuneable/mongod` stamped with its build id (commit, patch hash, profile). Unchanged patch means no rebuild. The persistent cache defaults to `/proj/<project>/tuneable/mongod-cache`, auto-detected from the CloudLab project directory mounted on the node, so a reimaged node costs a copy rather than a rebuild; `--cache DIR` overrides it and `--no-cache` disables it.
3. Once per run: `./run_all_cloudlab.sh <user@host> <key> <label> config_mongodb_global.yaml`. Each mongod starts with `slowOpSampleRate=0.001`: at the default of logging every operation over 100 ms, the leader of a 31-minute chameleon day sequence wrote 3.9 GB of slow-query lines (1.95 million of the first 2 million lines), since a majority write under geo already waits about 60 ms; slow-operation counts quoted above for earlier runs were taken unsampled. The experiment itself goes through `run_all_cloudlab_sweep.sh` with `--modes "weakest;strongest;pileus;chameleon"` over `config_mongodb_loadsweep.yaml` and `config_mongodb_global.yaml`; the invocations, including the sMax sensitivity ladder around 450, are listed at the end of README.md. The runner checks for `~/tuneable/mongod`, applies the delay rules, and the remote launcher raises the open-file soft limit to 64000, starts every mongod with `--nounixsocket` (five processes on one port would otherwise race on `/tmp/mongodb-<port>.sock`, an intermittent startup failure), waits for every mongod to accept connections before initiating, (the default 1024 caps mongod at 409 concurrent connections, one per in-flight command, which the driver pools exceed under load), starts the five mongods, initiates the replica set with tags and priorities, loads the key space with w:majority, runs the WorkloadDriver, and shuts the mongods down. The Java jar is still built and shipped per run, as before, so the sweep script's `--jar` flow is unchanged.
4. After a run stopped prematurely (Ctrl-C on the orchestrator, a dropped ssh, a hung driver): `./clean_cloudlab.sh <user@host> <key>`. Kills the `tuneable` tmux session and the run's processes (mongods or ServerNode JVMs, WorkloadDriver, MongoClusterAdmin), clears the tc/netem rules on loopback, deletes `mongo_data/` directories, and verifies the node is clean. Run directories without `run_info.txt` are reported and kept unless `--purge-incomplete` is passed; `--dry-run` only reports. It does not touch finished runs, the built mongod, the bazel cache, or a running build.
